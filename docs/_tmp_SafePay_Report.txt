Abstract
SafePay is an AI-powered secure digital payment platform designed to address the rapidly growing problem of financial fraud in India's digital payments ecosystem. With over ₹20,000 crore lost annually to digital fraud, traditional systems that rely on static KYC checks and rule-based fraud detection are no longer sufficient. SafePay introduces a multi-layered defence architecture combining Behavioural Biometrics, Machine Learning-based fraud scoring, Blockchain-backed cross-institution signal sharing, and Federated Learning — all orchestrated through a GenAI agent pipeline.
The platform provides real-time transaction risk scoring with a target latency of under 500ms, explainable AI decisions using SHAP values for regulatory compliance, and a privacy-preserving cross-bank fraud intelligence network using anonymised blockchain signals — zero raw PII ever leaves any institution. SafePay is built on a production-grade, fully containerised stack: Next.js 14 (frontend), FastAPI (backend), XGBoost + Isolation Forest (ML), Solidity/Hardhat (blockchain), Flower (federated learning), PostgreSQL + Redis (data layer), and Docker (infrastructure).
This report documents the complete design, architecture, implementation, and validation of SafePay — from the Phase 0 monorepo scaffold through the complete authentication system, wallet and payments engine, and ML fraud detection service built and tested by the team.

Chapter 1 — Introduction
1.1 Background and Motivation
The proliferation of digital payment systems in India — accelerated by UPI, digital wallets, and mobile banking — has created an enormous attack surface for financial fraudsters. According to the Reserve Bank of India (RBI) Annual Report 2024, digital fraud cases have grown at over 45% CAGR in the past three years, with losses exceeding ₹20,000 crore annually.
Traditional fraud detection systems suffer from three fundamental limitations:
Reactive by design — they catch fraud after the fact (24–72 hours) rather than preventing it in real-time
Data silos — each bank's model sees only its own transaction history; a fraudster who has never attacked Bank A is invisible to Bank A's model
Static KYC — identity verification happens once at registration (face + document), not continuously throughout the user session
1.2 Problem Statement
Design and implement a production-grade AI-powered payment platform that: (a) detects fraud in real-time at transaction time, not hours later; (b) uses behavioural signals captured continuously during the session rather than only at registration; (c) shares anonymised fraud intelligence across institutions without compromising user privacy; and (d) provides human-readable explanations for every block decision to meet regulatory requirements.
1.3 Objectives
Build a full-stack secure payment platform with complete P2P, merchant, and UPI payment flows
Implement a multi-signal fraud scoring engine using XGBoost, Isolation Forest, and behavioural biometrics
Achieve sub-500ms end-to-end risk scoring latency
Implement explainable fraud decisions using SHAP values for audit and compliance
Build a privacy-preserving cross-bank fraud signal network using Ethereum smart contracts
Implement Federated Learning to improve the fraud model without sharing raw transaction data across institutions
Design and deploy a GenAI agent orchestration layer for intelligent fraud case management
1.4 Scope
This project covers:

Frontend dashboard (Next.js 14) for both end-users and fraud analyst SOC console

Chapter 2 — Literature Review
2.1 Credit Card Fraud Detection — Survey
Existing surveys (Journal of King Saud University, 2022) establish that supervised ML approaches outperform rule-based systems for fraud detection. XGBoost and LightGBM consistently achieve AUC-ROC > 0.92 on benchmark datasets. However, these models operate in batch mode, not real-time, and are trained on centralised datasets — both limitations that SafePay directly addresses.
2.2 Behavioural Biometrics for Continuous Authentication
Research (IEEE Transactions on Information Forensics and Security, 2022) demonstrates that keystroke dynamics (dwell time, flight time, digraph latency) and touch biometrics (swipe pressure, velocity, gesture shape) can uniquely identify users with >95% accuracy after 20 training sessions. SafePay implements this as a JavaScript SDK capturing telemetry throughout the session — not just at login.
2.3 Federated Learning
McMahan et al. (Google Brain, ICML 2021) introduced FedAvg — the algorithm SafePay uses to aggregate model updates across bank clients without sharing raw transaction data. Key finding: federated models achieve within 2% accuracy of centrally-trained models while preserving data locality.
2.4 Blockchain for Financial Fraud Intelligence
Springer Financial Innovation (2023) proposes blockchain as a tamper-proof, decentralised ledger for cross-institution fraud signals. Privacy is maintained by publishing only keccak256 hashes of entity identifiers — never raw PII. SafePay implements exactly this architecture via Solidity smart contracts.
2.5 Explainable AI for Fraud Decisions
Lundberg & Lee (NeurIPS 2017) introduced SHAP values as a unified approach to model explanation. RBI guidelines increasingly require explainability for automated financial decisions — SafePay integrates SHAP into every block/challenge decision so users and compliance officers receive a plain-language reason.

RBAC middleware with 5 roles: user, merchant, fraud_analyst, compliance_officer, admin
Rate limiting: 10 req/min on auth endpoints, 60 req/min general, Redis sliding window
3.4 GenAI Agent Architecture
SafePay's fraud decision pipeline is orchestrated by a LangChain agent that wraps all backend modules as callable tools:
Tool 1: score_biometrics — calls ml-service /score with behavioural feature vector
Tool 2: check_blockchain — queries Solidity contract for cross-bank fraud signal
Tool 3: score_transaction — weighted composite risk calculation (35/30/20/15 weights)
Guardrail: validates every LLM output — no PII in response, confidence score present, reason non-empty
Human Handoff: confidence < 0.5 or HIGH_FRAUD category → escalate to Fraud Operations Team

6.3 Key Technical Decisions and Their Rationale
6.3.1 Async SQLAlchemy + asyncpg
FastAPI's async architecture requires a fully async database driver. Using synchronous psycopg2 in Uvicorn's event loop would block the entire server thread. SQLAlchemy 2.0's async engine with asyncpg resolved this.
6.3.2 Row-Level Locking for Wallet Operations
Standard read-then-write patterns for balance updates create a race condition: two simultaneous withdrawal requests can both read the same balance, both see sufficient funds, and both debit — resulting in a negative balance. SELECT ... FOR UPDATE locks the wallet row for the duration of the transaction, preventing this entirely.
6.3.3 Idempotency Keys on All Payment Endpoints
In mobile networks, requests are retried on timeout. Without idempotency, a user tapping 'Send' on a slow connection might trigger two transfers. Every payment endpoint checks for an existing transaction with the same idempotency_key before executing, returning the original result on duplicates.
6.3.4 SQLAlchemy Enum values_callable
PostgreSQL enums are case-sensitive. Python enum members (ACTIVE, PENDING) don't automatically map to their lowercase values (active, pending) stored in Postgres. Adding values_callable=lambda e: [x.value for x in e] to every Enum() column resolved 3 separate crashes during Phase 1 and Phase 2 development.
6.3.5 Separate Database URLs for App vs Alembic
FastAPI uses asyncpg (async driver, connection string: postgresql+asyncpg://...). Alembic requires psycopg2 (sync driver). Sharing one DATABASE_URL caused both to fail in alternation. The permanent fix was two separate environment variables: DATABASE_URL (async, for the app) and ALEMBIC_DATABASE_URL (sync, for migrations only).

8.3 Discussion
The phase-driven development methodology proved highly effective for a 3-person FYP team. By verifying each phase's exit criteria with real API calls before moving on, the team avoided accumulating unverified assumptions that would have manifested as hard-to-diagnose bugs in later phases.
The most significant technical challenge was the SQLAlchemy enum casing issue (Python enum .name vs .value vs Postgres enum values) which manifested in 3 separate tables. The systematic fix — applying values_callable to every Enum() column — eliminated the entire class of bug rather than patching individual occurrences.
Chapter 9 — Conclusion and Future Work
9.1 Conclusion
SafePay demonstrates that a production-grade AI-powered payment platform with multi-layer fraud detection is achievable within a final year project scope, provided the architecture decisions are made correctly upfront. The microservices monorepo structure, async-first backend, and phase-driven validation approach enabled the team to build and verify a substantial system within the academic timeline.
The combination of behavioural biometrics (Phase 3), XGBoost fraud scoring (Phase 4), SHAP explainability (Phase 5), blockchain signal sharing (Phase 6), and federated learning (Phase 7) represents a novel, multi-layered approach that addresses the genuine research gaps identified in Chapter 2 — none of the existing systems combine all five layers in a single real-time pipeline.
